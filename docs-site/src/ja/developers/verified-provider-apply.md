# 認証済みプロバイダーの申請

試作のページ `/experiment/apply-provider` では、提供者が「id.ldas.jp で確認済み」の
マーク付きで登録されるよう申請できます。このページでは、よく聞かれる 2 つの点を説明します。
なぜ **ウォレットの署名** を求めるのか。なぜ **サイト上部の LDAS ID ボタンが消えた** のか。

コード: `src/experiment/verified-provider/Page.tsx`（ページ）、
`worker/applicationFlow.ts` と `worker/walletSignature.ts`（確認の処理）、
`worker/index.ts` の `/api/provider-application/*`。運営者の手順はポータルのブランチの
`docs/verified-providers.md` にあります。ポータルのコミット: `c2965491` (branch `feat/verified-mark`)。

## なぜウォレットの署名を求めるのか

登録簿は、ウォレットのアドレスと名前を結び付けます。
そのため、申請者がそのウォレットを本当に持っていることを、ポータルが確かめる必要があります。

- **ウォレットの接続は、自己申告にすぎません。** MetaMask をつなぐと、ブラウザがページに
  アドレスを伝えます。サーバはその証拠を受け取りません。どんなスクリプトでも、
  好きなアドレスをサーバに送れます。
- **署名は、サーバが自分で確かめられる証拠です。** Worker は、使い捨ての乱数（ノンス）を
  含む短い文をページに渡します。ウォレットがそれに署名します（`personal_sign`、EIP-191）。
  Worker は、文と署名だけから、どのアドレスが署名したかを計算します。
  それが文の中のアドレスと違えば、申請はそこで止まります。

署名には費用がかからず、チェーンには何も書き込まれません。ウォレットに出る文は次のとおりです。

```
Clio-X の認証済みプロバイダーに申し込みます。
Apply to be a verified Clio-X provider.

署名には費用がかからず、チェーンには何も書き込まれません。
Signing costs nothing and writes nothing on chain.

Address: 0x…
Nonce: <16 進 32 文字>
URI: https://cliox.ldas.jp
Issued At: 2026-11-25T…Z
```

この変更の前（案 A）は、接続中のウォレットと、id.ldas.jp の証明書に書かれたウォレットを
比べていました。これには 2 つの問題がありました。接続中のアドレスは結局ブラウザの申告のままでした。
また、id.ldas.jp はウォレットの連携をやめる予定で、証明書にウォレットが入らなくなります。

## 4 段階の確認

4 つとも Worker の中で行います。保存するのは、10 分で切れる封をした Cookie だけです。

1. **開始**: Worker がノンスと文を発行します。同じノンスを、あとで id.ldas.jp の
   OID4VP のノンスにも使います。これで 2 つの証明が 1 件の申請に結び付きます。
2. **ウォレットの署名**: Worker は、自分の封をした状態から文を作り直します
   （ページから送られた文は信用しません）。そして署名者を計算します。
3. **LDAS ID**: id.ldas.jp の証明書を、これまでどおり確かめます（発行者の署名、
   鍵の結び付け、ノンス、宛先、失効）。名前と、どう確認された人かが分かります。
   証明書にウォレットが入っていても使いません。
4. **送信**: 署名と証明書が同じノンスを持つこと、同意があることを確かめます。
   ノンスを使い切り（2 回目の送信は断ります）、HMAC で封をした登録簿の 1 行を
   運営者にメールで送ります。署名と証明書は捨てます。

ブランチで測ったこと: Worker のテスト `node --test worker/*.test.mjs`（20 件すべて通過）。
署名の確認には `@noble/curves` と `@noble/hashes` を使います（Worker の配布物で gzip 後 約 13 kB）。
署名者の計算は、ノート PC の Node 25 で初回 約 15 ms、2 回目以降 約 1 ms でした。
Workers の上での時間はまだ測っていません。

## なぜ上部の LDAS ID ボタンを隠したのか

上部の LDAS ID ボタン（`src/components/Header/LdasIdButton.tsx`）は、
チャットボットのサインインのために付けたものです。本番は `CHATBOT_REQUIRE_SIGNIN = "false"`
（`wrangler.jsonc`）で動いているので、本番ではこのボタンに役目がありませんでした。
そのうえ、提供者の申請はこのボタンから行うものだと思われがちでした。

ボタンは、チャットボットのサインインが必要かどうかを Worker に尋ね
（`GET /api/chatbot/signin`）、必要なときだけ表示されるようにしました。
申請のページには専用の「LDAS ID で確認する」の段階があるので、困ることはありません。
