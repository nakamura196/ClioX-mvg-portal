# Internationalization (i18n)

The portal ships English (`en`, default) and Japanese (`ja`). English keeps the
unprefixed paths, Japanese lives under `/ja/*`.

## Moving parts

| File                                         | Role                                                                                                 |
| -------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `next.config.js` → `i18n`                    | Next.js locale routing. Build-time; must list the same locales as `src/i18n/index.ts`.               |
| `src/i18n/index.ts`                          | next-i18next config passed to `appWithTranslation`. Bundles the dictionaries inline via `resources`. |
| `src/i18n/locales/{en,ja}.json`              | UI string dictionary (the `common` namespace).                                                       |
| `src/i18n/mergeLocaleContent.ts`             | Merges a sparse locale override on top of an English `content/*.json` file.                          |
| `src/i18n/useSearchLabel.ts`                 | Translates search filter/sort labels that live in module-level constants.                            |
| `src/components/Header/LanguageSwitcher.tsx` | The `EN / 日本語` switcher in the header.                                                            |
| `content/*.ja.json`                          | Japanese overrides for page copy that lives in `content/`.                                           |

`localeDetection` is off: `/` always serves English and the visitor opts into
Japanese through the switcher, rather than being redirected by
`Accept-Language`.

## Why translations are bundled inline

`src/i18n/index.ts` passes the dictionaries to next-i18next as `resources`
instead of letting the filesystem backend read `public/locales`. That is what
lets every page work **without** adding `serverSideTranslations()` to its
`getStaticProps` / `getServerSideProps`. Most pages here have no data-fetching
function at all, so the usual next-i18next wiring would mean adding one to each
of them — a large diff against upstream for no benefit at this dictionary size.

If the dictionaries ever grow large enough that shipping every locale to every
visitor matters, switch to `serverSideTranslations()` per page and drop
`resources`.

## Adding a string

1. Add the key to **both** `src/i18n/locales/en.json` and `ja.json`.
2. In the component:

   ```tsx
   import { useTranslation } from 'react-i18next'

   const { t } = useTranslation('common')
   return <span>{t('footer.legal')}</span>
   ```

Import `useTranslation` from `react-i18next`, not `next-i18next/pages` — only
`_app.tsx` needs the latter (see the note on module resolution below).

## Translating `content/*.json` page copy

Page copy that already lives in `content/` is translated by adding a sibling
`*.ja.json` holding **only** the strings that change:

```jsonc
// content/site.json          (English, upstream)
{ "menu": [{ "name": "Catalogue", "link": "/search?..." }] }

// content/site.ja.json       (override)
{ "menu": [{ "name": "カタログ" }] }
```

`mergeLocaleContent` merges objects key by key and **arrays by index**, so links,
images and untranslated fields fall through to English. The index coupling is
the one thing to watch: if upstream reorders an array in `content/site.json`,
the matching `.ja.json` has to be reordered too.

Two helpers consume these files:

- `useLocaleContent(en, ja)` — the general case, used by pages and components
  that import a `content/*.json` directly.
- `useLandingPageContent()` — the landing page, whose content is shared by six
  components.

Currently overridden: `content/site.ja.json`, `content/pages/home/landing-page.ja.json`,
the publish flow (`content/publish/*.ja.json`, `content/price.ja.json`), the asset
download/compute/edit forms (`content/pages/{startDownloadDataset,startComputeDataset,editMetadata,editComputeDataset,edit,history}.ja.json`)
and the standalone pages (`bookmarks`, `verify`, `faucet`, `chatbot`,
`textAnalysis`, `visualizations`, `cameroonGazette`).

### Markdown pages

Legal pages are translated as sibling files rather than JSON overrides:

- `content/pages/imprint.ja.md`, `terms.ja.md` — picked up by
  `getPageBySlug(slug, subDir, locale)`, which prefers `<slug>.<locale>.md` and
  falls back to English. `getAllPages()` filters `*.<lang>.md` out so they do not
  become routes of their own.
- `content/pages/privacy/ja.md`, `cookies/ja.md` — these pages carry the
  language _in_ the slug (`/privacy/en`, `/privacy/ja`) and already had a
  language switcher; the Japanese version is registered in the matching
  `policies.json`.

Each translated legal page opens with a note that the translation is provided
for convenience and the English version prevails — matching what the terms
themselves say in sections 1.2.2 and 13.8. **The translations have not been
reviewed by counsel.**

## Adding a locale

1. Add the code to `locales` in `src/i18n/index.ts` **and** to `i18n.locales`
   in `next.config.js`.
2. Add `src/i18n/locales/<code>.json` and register it in `resources`.
3. Add a display name in `localeNames`.
4. Optionally add `content/*.<code>.json` overrides and extend the `locale ===
'ja'` checks in `src/@context/MarketMetadata/index.tsx` and
   `src/@utils/landingPageContent.ts`.

## What is deliberately left in English

- **Option strings that double as form values.** `content/publish/form.json`'s
  `options` arrays (`Dataset`/`Algorithm`/`SaaS`, `Access`/`Compute`,
  `Forever`/`1 hour`/…) are stored verbatim in the published asset and compared
  against literals in code (`src/@utils/ddo.ts`), so the JSON keeps them in
  English. Where the component separates label from value — the box selections
  in `Publish/Metadata` and `Publish/Services` — only the visible `title` is
  translated, via `publish.boxTitles.*`. Module-level constants derived from
  these options read `contentEn`, never the localized content.
- **On-chain metadata.** The Data NFT name, symbol and description in
  `src/@utils/nft.ts` are written to the blockchain, not rendered chrome.
- **Wallet connection UI.** "Connect Wallet" and the wallet modal come from
  connectkit and would need that library's own localization.
- **Editorial content** under `content/resources/` (articles, glossary,
  research) — that is a content translation job, not a UI one.

## Two constraints worth knowing

**`@types/react` had to be bumped.** react-i18next augments the `react` module
with a `React.JSX` namespace. `@types/react` 18.0.25 predates that namespace, so
the augmentation created it from scratch — with none of React's real JSX
members — and every JSX element in the project lost `children` and `key`
typing (~260 type errors). `@types/react` ≥ 18.2.8 declares `React.JSX` itself,
so the augmentation merges into it correctly. The bump also surfaced genuine
latent type errors in `src/components/Resources/*`, where `motion` variants
objects are now annotated as `Variants` so the cubic-bezier `ease` arrays infer
as tuples.

**`next-i18next/pages` is declared manually.** next-i18next v16 publishes its
Pages Router entry only through the package `exports` map, which this project's
`moduleResolution: "node"` cannot read. Mapping the subpath through tsconfig
`paths` does not work either: Next.js feeds tsconfig paths into webpack, which
then tries to parse the `.d.cts` declaration file as runtime code. So
`src/@types/next-i18next.d.ts` declares the small surface `_app.tsx` uses, and
webpack resolves the real module on its own.

## Tests

`.jest/jest.setup.tsx` initializes the default i18next instance with the English
dictionary. Components call `useTranslation()` without a provider, so without
that init `t()` returns the key and every assertion on visible copy fails.

`InputRadio` derives checkbox/radio ids from the field name instead of
`slugify(option)` — slugify drops non-latin scripts, which would collapse every
Japanese option to the same empty id and break label/input association.
