## 設計

### (1) 契約の構成

補助を受けられる人の決め方を、スキームごとに 3 つから選ぶ。

- **0「誰でも」** — 今と同じ。
- **1「会員名簿」** — 契約の名簿にあるウォレットだけが補助を受けられる。名簿を変えられるのは運営者（中村）だけ。
- **2「id.ldas.jp で承認された人」（案Y）** — id.ldas.jp が署名した「この人は会員」という証明を持つウォレットだけが補助を受けられる。

決まりごと:

- **方式はスキームを作るときに決め、後から変えられない。** 預けた後で条件が変わると、預けた人への説明が崩れるため。試すときは、スキームを作り直せばよい。
- 値引き・上乗せは、どの方式でも誰でも対象。
- 対象外の人も、補助なしの値段で払える。
- **方式どうしは混ざらない。** 名簿の人が案Y のスキームで払っても、名簿だけでは補助は出ない。逆も同じ。
- 名簿の記録: 足した時刻（「いつから会員か」）を契約に持たせる。足す・外すの記録は、すべてチェーンに残る。足せるのは運営者だけなので、「誰が足したか」は中村に決まる。
- 支払いの記録に「どの方式で補助を受けたか」（なし・名簿・id.ldas.jp）を残す。台帳の列にそのまま出せる。
- 案Y の署名者のアドレスは、契約全体で 1 つ。変えられるのは運営者だけ。0 にすると、案Y のスキームの補助が全部止まる（緊急停止）。
- 名前や ORCID から作った値（ハッシュ値など）も、チェーンに載せない。ORCID は数が限られていて、総当たりで当てられるため。

### (2) id.ldas.jp 側の最小の変更（案Y）

Clio-X の名前・契約アドレス・チェーンを、id.ldas.jp に入れない。足す窓口は 2 つだけ。

- `GET /api/attestation/info` — 署名者のアドレスと、署名の形式を返す。
- `POST /api/attestation` — 次の流れで証明を出す。
  1. 利用者が「id.ldas.jp: このウォレットが承認済み会員のものか確かめてください（時刻 …）」という文に、MetaMask で署名する。
  2. id.ldas.jp は、時刻が 5 分以内か、署名がそのウォレットのものかを確かめる。
  3. そのウォレットが結びつけられた人で、管理者が手で承認していれば（`approved_by` 欄がある）、`{wallet, validUntil, signature}` を返す。有効期限は 1 時間。

窓口の性質:

- Cookie は使わない。ブラウザから呼べる範囲（CORS）は全部許可（`*`）でかまわない。
- 使い捨ての番号（nonce）は保存しない。署名を盗まれても、出る証明はそのウォレットの持ち主しか使えないため。
- 断るときの理由は 1 種類にまとめる。アドレスだけで「会員かどうか」を引ける窓口は作らない。

署名の形式は EIP-712（中身の項目と型を決めて署名する、イーサリアムの標準の形式）。

- domain（署名の宛先を示す欄）は `{name: "id.ldas.jp", version: "1"}` だけにする。
- verifyingContract（宛先の契約）も chainId（チェーンの番号）も入れない。「会員である」はチェーンをまたいで同じ事実なので、チェーンに縛る必要がないため。
- 中身は `Member{wallet, validUntil}`。

署名の鍵:

- 今の VC の鍵は Ed25519 で、契約の中では確かめられない。
- そこで secp256k1（イーサリアムと同じ種類の鍵）の鍵を、VC の鍵とは別に作る。
- 正本は 1Password に置く。Worker の秘密情報へは `op read` 経由で入れる。ディスクには残さない。

注: id.ldas.jp は 2026-10-02 から「ORCID があれば自動で approved」になっている。そのため、`status=approved` だけでは「中村が確かめた人」の意味にならない。判定には `approved_by` 欄を使う。

### (3) 画面の見え方

- **スキームを作るとき**: 「補助を受けられる人: 誰でも／会員名簿の人／id.ldas.jp で承認された人」から選ぶ。「作った後は変えられません」と添える。
- **スキームの見出し**: 方式を文で出す。読めないときは「確認できません」と出し、払えなくする（「誰でも」とはみなさない）。
- **払う欄（名簿のスキーム）**: 「名簿にあります（10/06 から）→ 補助 X PLAY」か、「名簿にありません → 補助なしで Y PLAY」と出す。
- **払う欄（案Y のスキーム）**: 「id.ldas.jp で確かめる」を押し、MetaMask で 1 回署名すると「確認できました（○時○分まで）」と出て、見積もりが補助込みに変わる。確かめなければ、補助なしの値段で払える。
- **払うボタン**: 「最大 Z PLAY を払う」と出し、この額を上限として契約に渡す。
- **台帳**: 「補助の資格」の列を足す（名簿／id.ldas.jp／—）。
- **会員名簿の欄**: アドレスと「いつから会員か」を出す（名前は出さない）。運営者には「足す・外す」が出る。

## 標準との関係

DID/VC の標準だけでは、契約が「補助を出すかどうか」を決められない。理由は 3 つある。

- 今の VC の署名は Ed25519（did:web で使っている署名の方式）。イーサリアムの契約には、これを確かめる組み込みの機能が無い。Solidity で書いた実装はあるが、ガス代は数十万〜100 万単位と言われている（**測っていない**）。
- VC は JWT（署名つきの JSON を base64 で包んだ形式）なので、契約の中でほどいて項目を読むのは重く、誤りやすい。
- チェーンの外で VC を確かめても、契約はその結果をそのままでは信じられない。結局「誰かが署名した結果を契約が確かめる」形になる。それが案Y。

案Y で独自なのは、2 点だけ。

- id.ldas.jp の発行窓口。
- 署名する中身の型 `Member{wallet, validUntil}`（項目は 2 つ）。

それ以外は標準に乗っている。

- 署名の形式は EIP-712（イーサリアムで、署名する中身の項目と型を決めて署名する標準の形式。MetaMask や ethers がそのまま扱える）。
- 主体（誰についての証明か）は、今の VC と同じ did:pkh のウォレット。案Y は「今の VC と同じ主張を、契約が読める形で言い直したもの」と言える。

VC の署名そのものを EIP-712 で付ける仕様案もある（EthereumEip712Signature2021）。W3C の正式な勧告ではなく、検討段階の草案だと理解しているが、**位置づけは確かめていない**。この案では VC の全項目を型に書くので、契約側の処理は案Y より大きくなる。そのため今回は使わない。

採用するときの別案として、EAS（Ethereum Attestation Service。誰でも使える「証明の記録」用の共用の契約）がある。

- 中村が EAS の画面（easscan）から「このアドレスは会員」という証明を書けば、名簿の代わりになる。
- 標準の取り消しがあり、記録を公開の検索画面で見せられる。
- id.ldas.jp に手を入れずに済む。
- いっぽう、id.ldas.jp 自身が EAS に書く形は採らない。id.ldas.jp にガス代を払う鍵とチェーンの設定が要り、「汎用の認証サーバのままにする」という前提に反するため。
- EAS が Sepolia に置かれていることと、そのアドレスは**確かめていない**。

試した結果で、EAS に置き換えるかを検討する。

### EAS を推す理由

- **出し手への説明（問 2）が、標準の画面でそのまま見せられる。** EAS の証明には、書いた人（中村のアドレス）・書いた時刻・対象のアドレス・取り消した時刻が残り、easscan で誰でも見られる。名簿の台帳画面を自前で作らなくてよい。
- **id.ldas.jp を汎用のまま保てる。** 窓口も鍵も足さない。秘密情報が 1 つ減る。
- **取り消しが即時。** 案Y の「最大 1 時間有効」が無くなる。
- **問 A の心配が消える。** 他の案件で承認された人が混ざらない。
- DID／VC の役割は残る。中村が「この人を会員にするか」を判断するときの根拠（ORCID で確かめた人と、そのウォレットの結びつき）として、id.ldas.jp の VC を見る。チェーンには載せない。

### 契約がすること

- 払う人が、自分あての証明の番号（UID）を渡す。画面は EAS の検索窓口（easscan の GraphQL）で番号を探して渡す。検索窓口は画面の便利のためだけで、判定は契約がチェーン上の記録で行う。
- 契約は EAS から証明を読み、次をすべて満たせば補助を出す: 型（schema）が決めたものと一致 / 書いた人が運営者 / 対象が払う人 / 取り消されていない / 期限が切れていない。
- 型は中身を最小にする（例: `bool member`）。名前・ORCID・それらのハッシュ値は入れない（上の決まりと同じ）。
- EAS のアドレス・型の番号・運営者は、スキームではなく契約全体の設定にする。

### 確かめたこと（2026-10-08）

- Sepolia の `0xC2679fBD37d54388Ce493F1DB75320D236e1815e` に EAS がある。`VERSION()` は `0.26`、`getSchemaRegistry()` は `0x0a7E2Ff54e76B8E6659aedc9103FB21c038050D0`（chain-reader で読んだ。RPC は publicnode の 1 か所だけ）。
- 0.26 は古い版。`version()` と `getName()` は無かった（呼ぶと失敗した）。証明を読む関数の形が新しい版と同じかは、forge のテストで確かめる。
- EthereumEip712Signature2021 は W3C の作業部会ではなく、コミュニティグループ（CCG）の実験的な草案。仕様のページに「本番には使わない」とある。2021 年以降に進んだ様子は見つからなかった。

### まだ確かめていないこと

- EAS 0.26 の `getAttestation` の戻り値の形（forge で、Sepolia を写したローカルのチェーン上で確かめる）。
- 1 人を書くガス代。Sepolia ではテスト用の ETH で足りる見込み（5〜10 人）。
- easscan の Sepolia 版の検索窓口が、画面から使えるか（CORS）。使えなければ、運営者が番号を画面の設定に書く。

### 了承されたら変わること

- 方式は「0 誰でも／1 EAS の証明」の 2 つになる。案Y・名簿は作らない。
- id-ldas の `feat/member-voucher`（未コミット 3 件）は破棄する。`feat/attestation` も作らない。
- 実装の順番の 2（id-ldas）が無くなる。配備は、新しい契約 → ポータルの切り替え、の 2 段になる。

## 以前のレビューの指摘と、その取り込み方

| 指摘 | 取り込み方 |
|---|---|
| 払う額の上限がない | 払うときに「最大でいくらまで払うか」（maxPayerPays）を渡す。超えたら取引は失敗し、何も起きない。見積もりの後に、預け入れが尽きた・名簿から外れた、という場合に高く払わされるのを防ぐ |
| 方式が読めないとき「誰でも」扱いになる | 「確認できません」と出し、払えなくする |
| 案Y の支払いを別の方式のスキームで呼ぶと、黙って補助なしで通る | 失敗させる |
| 画面の「補助の対象です」が、契約の判定と食い違いうる | 名簿は契約から読む。案Y は「証明を渡すと見積もりを返す」読み出しを契約に足し、その結果をそのまま出す。画面独自の判定は持たない |
| 引換券（証明）の期限に上限がない | id.ldas.jp は 1 時間で出す。契約は 24 時間を超える期限を受け付けない（サーバの設定ミスの被害を 1 日に抑える）。期限内は何度でも使える（資格の証明であって、お金ではないため） |
| 預け入れの後で方式を変えられる | 作った後は変えられないようにした（問 B） |
| 証明がスキームや契約に縛られない | 意図どおりとした。「会員である」はスキームによらない事実のため |
| chainId に VC 用の設定を流用している | domain から chainId を外したので、問題がなくなる |

## 取り消しの効き方

- **名簿**: 外した瞬間から、補助が出なくなる。
- **案Y**: id.ldas.jp で外しても、すでに出た証明は最大 1 時間有効。急ぐときは、署名者を 0 にする（案Y のスキームの補助が全部止まる）。
- 鍵を差し替えるときは「新しい鍵を Worker に入れる → 契約の署名者を変える」の順で行う。

この違い自体が、試して比べる点の 1 つ。

## 却下した案・置き換えた案と、その理由

- **案A（ページだけで確かめる）** — 却下。契約は誰にでも同じ額を出すので、契約を直接呼べば誰でも補助を受けられる。資格の確認にならない。
- **案B（VC を貼ると、id.ldas.jp が 1 時間の引換券を出す）** — 案Y に置き換えた。理由は 3 つ。
  - id.ldas.jp に Clio-X 専用の処理（契約アドレス、cliox に固定した CORS、引換券の形式）が入る。
  - VC には名前と ORCID が平文で入っており、それを Clio-X 側に渡すことになる。
  - VC を貼る操作は、archivist には重い。
  - Sonnet が作った試作（id-ldas の `feat/member-voucher` ブランチ、`/api/voucher`）は消さずに置いておく。ただし使わない。
- **案C（運営者の許可リスト）** — 「会員名簿」として採用した。
- **案X（id.ldas.jp は VC を確かめるだけにして、引換券は Clio-X 側の別 Worker が出す）** — 却下。VC（名前入り）が Clio-X 側に渡ること、鍵と Worker が 2 つに増えることが理由。
- **Sonnet 版の gate 0/1/2（ブランチ `proto/member-gate`）** — 部品として使う。変える点は 3 つ。
  - 2 番の中身を、引換券から案Y に差し替え、署名を EIP-712 にする。
  - 方式をスキームを作るときに固定する。

## 実装（2026-10-09）

結論: EAS 方式で作り直しました。名簿と案Y のコードは契約から消えています（記録は `archive/member-gate-roster-y`）。Sepolia では何も実行していません。

### 作ったもの

- 契約 `contracts/carbon-choice/src/GreenFeeDemo.sol`
  - 補助を受けられる人は、スキームを作るときに決めます（0 誰でも、1 EAS の証明）。作った後は変えられません。変える関数がありません。
  - 契約全体の設定は、運営者だけが変えられます。EAS のアドレスと型の番号（`setEas`）、信用する書き手（`setAttester`）の 2 つです。書き手を 0 にすると、会員向けスキームの補助が全部止まります（緊急停止）。
  - 払う人は証明の番号を渡します（`payMember`）。契約が EAS から証明を読み、次をすべて確かめます。型が一致、書き手が運営者、対象が払う人、取り消されていない、期限が切れていない。
  - 番号が 0 なら、補助なしの値段で払えます。番号があるのに確認が通らなければ、理由つきで失敗します。会員のつもりで、黙って全額を払わされることはありません。
  - 会員向けでないスキームに `payMember` を使うと失敗します。
  - 払う額の上限（`maxPayerPays`）を超えるなら失敗します。誰でもスキームには `payUpTo` を使います。
  - 画面が使う読み出し: `isMember(払う人, 番号)` は「通るか」と「理由の番号」を返します。`quoteFor(...)` は見積もりを返します。
  - 支払いの記録に、補助の根拠（0 なし、1 EAS）と証明の番号を残します。
- 型は `bool member`、resolver なし、取り消し可。型の番号は `0x751f5a7e…130d`（テストで `keccak256("bool member", 0x0, true)` から計算して一致を確認）。
- スクリプト（実行していません）: `script/EasMember.s.sol`（型の登録・会員の証明を書く・取り消す）、`eas-member.zsh`（鍵を 1Password から取る起動用）、`script/DeployGreenFee.s.sol`（EAS・型・書き手の設定と、会員向けスキーム #2 の作成を追加）。
- ポータル `GreenFee.tsx` ほか
  - スキームを作るとき「誰でも／EAS の会員証明がある人」を選びます。「作った後は変えられません」と添えています。
  - スキームの見出しに、受けられる人を文で出します。読めないときは「確認できません」と出し、払えなくします。
  - 払う欄は、払う人あての証明の番号を easscan の検索窓口で探し、契約の `isMember` の答えをそのまま出します。画面独自の判定はありません。自動で見つからないときのために、番号を入れる欄もあります。
  - 払うボタンは「最大 Z PLAY」と出し、その額を上限として契約に渡します。
  - 台帳に「補助の資格」の列があり、EAS の支払いは easscan の証明へのリンクです。

### 運営者の手順

1. 一度だけ型を登録する: `zsh eas-member.zsh register`（出る番号が `0x751f5a7e…130d` と一致しないと止まります）。
2. 契約を配備する: `deploy-green-fee.zsh`。EAS・型・書き手（既定は配備した鍵）が設定されます。
3. 会員を足す: `zsh eas-member.zsh attest 0x（ウォレット）`。easscan の画面からも書けます。
4. 会員を外す: `zsh eas-member.zsh revoke 0x（証明の番号）`。すぐ補助が止まります。
5. 全部止める: `setAttester(0x0)`。

### 確かめたこと

- テスト: `forge test` は 34 件が通過、2 件はネットワーク用で既定では飛ばします。EAS の模擬（MockEAS）で、会員は補助あり。型違い・書き手違い・別の人あて・取り消し・期限切れ・書き手 0 は、番号があれば失敗。番号 0 は全額。誰でもスキームでの拒否、方式の固定、上限、支払い記録の項目も見ています。
- **EAS 0.26 の `getAttestation` の戻り値の形は、新しい版と同じでした。** Sepolia に実在する証明（easscan で見つけた 1 件）を、契約の読み取り部分（`IEAS`）で読み、型・書き手・対象・取り消し時刻・期限まで一致しました（`FORK=1 forge test --fork-url … --match-contract Fork`）。存在しない番号は失敗せず、中身がすべて 0 で返ります。契約はこれも「見つからない」として扱います。
- Sepolia を写したローカルのチェーンに、実物の EAS を使って型の登録・配備・証明・支払いを通しました。会員の支払いは成功し、記録に補助の根拠 1 と証明の番号が入りました。上限を低くすると失敗しました。
- **easscan の検索窓口は、ブラウザから使えます（CORS）。** 許可するオリジンは `*` で、POST と content-type の事前確認が通りました。検索の条件では、アドレスを大文字小文字の混ざった形（チェックサム）にする必要があります。小文字だと 0 件になります。
- ポータルをローカルで開き、会員向けスキームの見出しと台帳の「補助の資格」の列（EAS のリンク）を目で確認しました。`tsc`・`eslint`・`prettier`・greenFee の jest（7 件）は通っています。
